# H2A interop vectors

Normative test data for [ADR-014](../spec/adr/ADR-014-canonical-form.md): the canonical form every
H2A signature and hash is computed over, and the signature encoding `alg: "ES256"` denotes.

**An implementation is conformant if and only if it reproduces every vector byte-for-byte.** Prose
describes the canonical form; these files decide it.

```
vectors/vectors.json      the artifact — 9 canonicalisation vectors + signature vectors
vectors/VECTORS.sha256    sha256 of the above, for vendoring by digest
vectors/inputs/*.json     each vector's input, as authored bytes
generate.mjs              regenerates vectors.json (see "Trust" below)
verify-catches.mjs        asserts the `catches` metadata is true, for TypeScript
verify_catches.py         the same, for Python
```

## Consuming them

```js
const { canonicalization_vectors } = JSON.parse(fs.readFileSync("vectors/vectors.json", "utf8"));
for (const v of canonicalization_vectors) {
  assert.equal(myCanonicalize(JSON.parse(v.input_json)), v.canonical);
}
```

**Parse `input_json`. Do not read a pre-parsed value.** The field is a string holding the authored
text, and that is deliberate: JSON has a single number type, so the difference between `500.0` and
`500` — which vector 03 exists to test — survives only in the text. An earlier draft of this
directory stored inputs as parsed objects, and `JSON.stringify` flattened `500.0` to `500` and `-0`
to `0` on the way into the manifest. Both vectors still passed, because both sides of the comparison
had been normalised identically. They tested nothing. `verify_catches.py` is what caught it.

Each vector also carries `canonical_sha256`, so an implementation that cannot conveniently compare
strings can compare digests.

## The vectors

| id | what it pins | catches |
|---|---|---|
| `01-rfc8785-appendix-b` | RFC 8785's own published sample — numbers, escapes, ordering | `py-json-dumps` |
| `02-unicode-subject-name` | a performer's name with diacritics stays literal UTF-8 | `py-json-dumps` |
| `03-lease-cap-decimal` | `500.0` serialises as `500` | `py-json-dumps` |
| `04-mixed-case-keys` | sort by UTF-16 code unit, not by locale | `ts-localecompare` |
| `05-integer-like-keys` | `"10"` sorts before `"2"`; emit from the sorted sequence, never via an object | `ts-localecompare` |
| `06-nesting-null-empty` | nested objects inside arrays, `null`, `{}`, `[]` | — |
| `07-control-characters` | lowercase `\uhhhh`, the five short forms, the U+001F/U+0020 boundary | — |
| `08-number-forms` | `1e2`→`100`, `-0.0`→`0`, `1e21`→`1e+21` | `py-json-dumps` |
| `09-grant-signing-preimage` | a realistic grant: the detached-signature preimage of ADR-014 §3 | both |

`catches` names the estate implementations each vector detects, measured 5–6 August 2026:

- **`ts-localecompare`** — the ~8-line `JSON.stringify` replacer copied into all four h2a TypeScript
  reference services and into Bridle's `packages/core` (twice: `sign.ts` `canonical()` and `audit.ts`
  `stable()`). Sorts wrongly, serialises correctly.
- **`py-json-dumps`** — `reference/h2a_ref/verify.py:28`, `json.dumps(sort_keys=True)`. Sorts
  correctly, serialises wrongly.

The two are wrong in **disjoint** ways, and both agree with JCS on the payloads people test with.
That is why the divergence went unnoticed: it appears only on real names and real money.

## Signature vectors

ADR-014 §2 — `alg: "ES256"` is the JOSE fixed-width R‖S encoding, 64 bytes, never DER. The committed
acceptance matrix is the reason it matters:

```
der_verifier_accepts_der : true
der_verifier_accepts_raw : false     <- a conforming ES256 signer is rejected
raw_verifier_accepts_raw : true
raw_verifier_accepts_der : false     <- the estate's own signatures are rejected
```

The two encodings are mutually unverifiable. There is no partial credit and no graceful degradation.

`private_key_pem` is committed in plain text **on purpose**: every implementation must verify the
same bytes with the same key, so the key is published. It is a test key. It must never appear in a
deployed configuration, and CI greps for it outside this directory.

ECDSA is randomised, so the signature bytes cannot be regenerated deterministically. `generate.mjs`
therefore re-uses the committed signature as long as it still verifies, and only re-derives it if it
does not — otherwise `--check` could never be stable.

## Trust

`vectors.json` is generated by the `canonicalize` npm package, which on its own would prove only
"the estate agrees with one library". So before emitting a single byte, `generate.mjs` asserts that
its canonicaliser reproduces **RFC 8785's own published test data** exactly, and exits non-zero
otherwise. A non-conformant canonicaliser cannot write vectors.

That anchors the file to the RFC rather than to a dependency: swap the generator's canonicaliser for
any other conformant implementation and the output must be byte-identical.

```
node interop/generate.mjs           regenerate
node interop/generate.mjs --check   assert the committed files match (CI)
node interop/verify-catches.mjs     assert the catches metadata is true (TypeScript)
python interop/verify_catches.py    assert the catches metadata is true (Python)
```

`verify-catches` re-implements the two known-bad canonicalisers verbatim and asserts each one fails
**exactly** the vectors listed against it — no more, no fewer. Over-claims and under-claims both
fail. A vector that is supposed to catch a bug and quietly does not is worse than no vector at all,
because it reports green over a real divergence.

Both scripts will keep passing as the estate is ported, because they test the *metadata*, not the
estate. The job that tests the estate is **S1.X1**, which runs these vectors in Bridle's, hdicr's and
this repository's CI and fails on any divergence. That is what closes blocker B4.

## Vendoring

Vendor by digest, not by branch:

```sh
sha256sum -c VECTORS.sha256      # from interop/vectors/
```

`VECTORS.sha256` exists so a silent edit to the vectors fails every downstream build rather than
passing them. The vectors are covered by `.gitattributes -text`, so their bytes are identical on
every platform regardless of Git configuration.

### The pin

Every consuming repository holds a copy of `vectors.json` and runs `scripts/check-vectors-pinned.mjs`
against it in CI. That script is **byte-identical in h2a-protocol, bridle and hdicr**, and carries
the pin: the upstream commit and the expected SHA-256. It asserts three things, all hard failures —
the local copy matches the digest, upstream at the pinned commit matches the digest, and the two are
byte-identical. An unreachable upstream **fails**; it does not skip.

Without it, each repository validated its canonicaliser against a fixture only it controlled. Edit
bridle's copy to match a broken bridle canonicaliser and bridle stays green, hdicr stays green, this
repository stays green, and the estate is quietly back to four canonical forms — the same defect the
vectors exist to prevent, moved one level up.

**Changing the canonical form is therefore a deliberate three-repository operation:**

1. Edit the vectors here; regenerate `VECTORS.sha256`; commit and merge to `main`.
2. Take the resulting commit SHA. Update `UPSTREAM_COMMIT` and `EXPECTED_SHA256` in
   `scripts/check-vectors-pinned.mjs` **in this repository** — its own CI checks the pin, so a stale
   pin here goes red first.
3. Re-vendor the fixture and copy the same script, unchanged, into bridle and hdicr.

Each step is a reviewed diff. That cost is intentional: `vectors.json` is normative test data
(ADR-014 §4), so changing it is a specification change, and a specification change should not be able
to arrive in three repositories as a silent consequence of a green build.
